> 定位：**用户看不见的数据绝不丢，用户看得见的错必须说出口。**
> 不新增功能，只做正确性、数据安全、可感知体验与 1000+ Mod 下的性能。
> 明确不做：错误文案中文化（保留原文，另开版本统一处理）。

调研基线：`1.2.0`（commit `ae9c5ea`）。后端 9094 行 / 前端 renderer 11844 行。
所有条目均带文件行号，改完逐条对照验收标准。

## 阶段一 · 数据安全（P0）

这四条都会让用户真的丢东西，优先于一切。

### T1 `data.json` 读盘失败不再回落默认值

- **位置**：`backend/services/data_store.py:151-188`（`_read_data_raw`）
- **现状**：`OSError`（文件被占用 / 权限不足）时 `raw_text = None`，随后落到
  `_get_default_data()` 并写入 `_cache`。注释写着"不要碰原文件"，但**写路径没有兑现**：
  下一次 `set_mod_meta` / `set_mod_enabled` 就会拿这份空默认值把整份 `data.json`
  （合辑、自定义名称、标签）覆盖掉。
- **方案**：新增模块级 `_read_only_reason`。
  - 读盘 `OSError` → 记录原因，返回默认值的**深拷贝且不写入 `_cache`**；
  - `_write_data_raw` 在该状态下直接抛 `DataStoreReadOnlyError`；
  - 调用方（路由层）捕获后返回 409 + 中文原因。
- **验收**：`chmod`/占用模拟下改标签不落盘，原 `data.json` 字节不变；接口返回明确错误。

### T2 `data.json` 增加写前备份

- **位置**：`backend/services/data_store.py:191-209`（`_write_data_raw`）
- **现状**：只有"损坏时隔离"（`data.json.corrupt-*`），正常写盘不留上一版。一次逻辑
  bug 或误操作无法回滚。
- **方案**：写入成功后把*上一版*落到 `data.json.bak`（rename 前 `copy`，失败静默但不影响主流程）。
  仅保留一份，不滚动。
- **验收**：连续改两次，`.bak` 内容是倒数第二次的状态。

### T3 `addonlist.txt` 写失败必须如实回报

- **位置**：`mod_scanner.py:1492-1576`（`_write_addonlist`）、`1816-1853`（`apply_mod_prefs_to_addonlist`）
- **现状**：写盘异常只 `print`，`applied` 在写之前就算好了。游戏目录只读 / 文件被占用时
  接口仍返回"已应用 N 项"—— 这是"软件里禁用、游戏里照样加载"的头号根因。
- **方案**：`_write_addonlist` 返回 `bool`；`apply_mod_prefs_to_addonlist` 返回
  `(applied, written)`；路由层 `apply-prefs` 与 `set_mods_enabled` 在 `written=False` 时
  返回 500 + 明确原因，前端据此提示。
- **验收**：把 `addonlist.txt` 设为只读，点启用 → 界面报失败，不再假装成功。

### T4 `config.json` 原子写 + 解析失败不静默

- **位置**：`mod_scanner.py:2158-2175`（`_load_config` / `_save_config`）
- **现状**：`write_text` 直接覆盖，无 fsync；读失败 `except:` 静默丢掉 `addons_path`，
  用户表现为"每次启动都要重新选目录"。
- **方案**：抽 `_atomic_write_json()`（tmp + fsync + replace），读失败时打日志并在
  `data.json` 的 recovery 记录里留一条。
- **验收**：配置文件写坏后启动，日志有明确记录，不静默。

### T5 `requirements.txt` 补 `vpk`

- **位置**：`backend/requirements.txt`
- **现状**：只有 fastapi / uvicorn / python-multipart，而 `mod_scanner` 顶层
  `import vpk`。按 README `pip install -r` 装完直接 `ImportError`，只有打包版因为内置
  了 site-packages 才没事。
- **验收**：干净 venv 装完能 `python -c "import vpk"`。

## 阶段二 · 正确性缺陷（P1）

### T6 空目录 / 路径失效导致无限刷新

- **位置**：`mod_scanner.py:2208-2229`（`_sync_scan_manifest` 空 manifest 提前 return）、
  `main.py:1130-1132`（`no_previous_scan` → `changed: True`）
- **现状**：addons 目录不存在或为空时 manifest 从不落盘，`scan-status` 每次都回
  `changed: true`，前端 5 秒轮询一次就判一次 changed → 永久静默空转。全新用户首次打开即命中。
- **方案**：
  - 扫描结束时即使 `files` 为空也写入 manifest（带 `scanned_at`）；
  - `scan_status` 对"空 manifest + 目录确实为空/不存在"回 `changed: false, reason: not_configured`。
- **验收**：指向空目录，观察 30 秒内不再反复触发扫描。

### T7 缩略图接口的任意文件读取

- **位置**：`main.py:1214-1218`（`?path=`）、`1640-1646`（`?wid=`）
- **现状**：`path` 直接 `FileResponse`，没有限制在 addons / 缓存目录内；`wid` 直接拼路径。
  对比同文件 `_resolve_cover_path`（1188-1201）是拒绝目录名的，说明知道风险，只漏了这两处。
- **方案**：抽 `_ensure_under_roots(p, roots)`，`path` 必须落在 `addons_path` 或
  `_CACHE_DIR` 下；`wid` 加 `^[0-9]+$` 白名单。
- **验收**：`?path=C:\Windows\win.ini` 返回 403。

### T8 解析失败的 VPK 从列表移出，改为下方提示条说明原因与处理办法

- **位置**：`mod_scanner.py:2664-2666`（`_parse_vpk_fast` 异常 → `return None`）；
  前端 `MyModsPage.tsx` / 新增 `UnreadableNotice.tsx`
- **现状**：坏包直接丢条目，用户只会觉得"我明明装了"，连删或者禁用都做不到。
- **方案**：
  1. 后端解析失败时仍产出最小 Mod 对象，带 `unreadable: true`、`unreadable_reason`、
     `size_bytes` —— **不能只为了隐藏就重新丢条目**，否则提示条也拿不到文件名与大小；
  2. 前端在**展示层**过滤掉 `unreadable`（`visibleMods`），列表、筛选结果、
     「全部 / 自定义 / 工坊」以及冲突 / 重复 / 更新计数一律以 `visibleMods` 为准，
     避免出现「计数 121、列表只有 120」；
  3. 列表下方常驻提示条（`UnreadableNotice`）：逐个列出 `文件名` + `大小` +
     `解析失败，错误原因：xxx`，并给出四步处理办法（看大小 / 重下或重订阅 /
     别把压缩包改后缀 / 刷新重扫），修复前不消失；集合变化时「已收起」自动复位；
  4. 每条带「打开所在目录」（新增 `shell:showItemInFolder` IPC，直接定位到文件）
     与「删除文件」（经 `ConfirmDialog` 二次确认）—— 文件从列表消失后，这两个
     出口是用户在软件里唯一够得到它的方式；
  5. 扫出新坏包时弹一次 toast 指向下方提示条（同一批坏包不重复弹）。
- **验收**：放一个 0 字节 vpk 和一个垃圾内容 vpk，**列表中不出现任何卡片**，
  上方计数不含它们，下方提示条列出两条（文件名 / 大小 / 原因 / 两个按钮）；
  点「删除文件」确认后条目与文件一起消失；`verify_unreadable_vpk.py` 全绿。

### T9 纯数字文件名被误判为工坊 ID

- **位置**：`workshop_updates.py:65-133`（`collect_installed`）
- **现状**：addons 根目录下任何纯数字文件名都被当成工坊 ID，本地 `123456789.vpk`
  会被误查、误覆盖。
- **方案**：只在 `workshop/` 子目录里按 ID 识别；根目录的纯数字包按本地 Mod 处理。
- **验收**：`addons/123456789.vpk` 不出现在更新检查列表中。

### T10 Steam 入口文案改为「读取本机账号」

- **位置**：`main.py:1292-1345,1408-1449`、前端 `WorkshopPage` / `SettingsPage` 相关文案
- **现状**：只读 `loginusers.vdf` 把最近用户标成已登录，没有任何 token 或校验。
- **方案**：不假装登录。接口与 UI 文案统一为「读取本机账号」，说明"来自 Steam 本地
  配置文件，不代表已授权"。
- **验收**：界面上不再出现「登录」字样。

## 阶段三 · 出错必须说出口（P2）

### T11 打通 `store.error`（死通道）

- **位置**：`useStore.ts` 14 处 `set({ error })`（835/837/841/1395/1546/1556/1580/1596/1630/1665/1717/1985/2045/2094），
  全项目 **0 处读取**。
- **现状**：合辑切换失败、删除失败、设置保存失败、Steam 登录失败——全部静默。
- **方案**：`App.tsx` 挂一个全局 `ErrorBanner`，消费 `error` 并给「重试 / 关闭」；
  保持 `set({ error: null })` 的清理语义（已有 5 处）。
- **验收**：断开后端点删除，界面出现可读错误条。

### T12 「在浏览器打开」修复

- **位置**：`WorkshopPage.tsx:59-68`
- **现状**：调用 `(window as any).openExternal`，真实是 `window.electronAPI.openExternal`；
  回退的 `window.open` 又被 `setWindowOpenHandler → deny` 拦掉 → 点了永远没反应。
- **验收**：点击后系统浏览器打开工坊页。

### T13 设置页「自动检测」不再无条件显示成功

- **位置**：`SettingsPage.tsx:136-181`、`useStore.ts:1585-1598`
- **现状**：无论检测成功与否都显示「已保存 ✓」，失败只把按钮改成「保存失败」不给原因。
- **方案**：由 store 返回 `{ok, path, count}`，成功提示带扫到的 VPK 数量，失败保留原因。
- **验收**：填一个不存在的路径，提示失败且不显示 ✓。

### T14 弹窗可关闭性 + 焦点管理

- **位置**：`ConfirmDialog.tsx:85-103`、11 处 `modal-overlay`
- **现状**：
  - 只有 ConfirmDialog 认 Esc，其余 10 个弹窗只能点遮罩；
  - `ConfirmDialog` 的 Enter 是**无条件确认**，焦点在「取消」上也执行危险操作；
  - 无 `role="dialog"` / `aria-modal`，无焦点陷阱，Tab 可跑到背景页。
- **方案**：
  - 新增 `hooks/useModalA11y.ts`：Escape 关闭、Tab 循环、`role/aria-modal` 设置；
  - 四个主要弹窗（重命名 / 删除确认 / 重复详情 / 冲突详情）接入；
  - ConfirmDialog 的 Enter 改为"只有焦点在确认键上才确认"。
- **验收**：Esc 关弹窗；焦点在取消键按 Enter 不触发删除。

### T15 批量操作不再 N 次全量扫描

- **位置**：`MyModsPage.tsx:1185`（批量删除逐个 `deleteMod`，每个内部 `await fetchMods()`）
- **现状**：选 10 个 = 10 次全量扫描 + 10 次全量写盘。
- **方案**：新增 `deleteMods(names)` 串行执行、只在最后 `fetchMods()` 一次；批量改标签同理。
- **验收**：批量删 10 个只有一次列表刷新。

## 阶段四 · 性能（P3）

### T16 `scan-status` 轻量化

- **位置**：`main.py:1113-1179`
- **现状**：每 5 秒 3 次 glob + 逐 VPK `stat` + 构造两个完整 dict。1000 个 VPK 下持续抖动。
- **方案**：先比 `addons` 目录自身 mtime + 顶层 VPK 计数，未变直接回 `no_changes`；
  变了才走全量比对。
- **验收**：静态目录下 `scan-status` 单次耗时 < 5ms（1000 包）。

### T17 VPK 缓存加 LRU 上限

- **位置**：`mod_scanner.py:416-421`
- **现状**：`_VPK_INDEX_CACHE` / `_VPK_MANIFEST_CACHE` / `_VPK_METADATA_CACHE` 三份副本
  全部无上限、无淘汰，1000 个 Mod 常驻几百 MB～GB。
- **方案**：抽 `_BoundedCache`（OrderedDict，`max_entries` 默认 index 400 / manifest 800 /
  metadata 800），`get` 时 `move_to_end`。
- **验收**：`len(cache) <= max_entries` 恒成立，命中率在 bench 中不明显下降。

### T18 `_game_status_lock` 里的 I/O 移出锁

- **位置**：`main.py:408-520`
- **现状**：持锁状态下跑 `tasklist`（最长 6 秒）并调用写盘的重应用逻辑。每次 Mod 启停
  都走这条 → 「点开关没反应」。
- **方案**：锁外执行子进程与写盘，锁内只做结果回填；加"正在检查"标记避免并发重复拉。
- **验收**：模拟 tasklist 卡 5 秒时，启停请求仍在 300ms 内返回。

### T19 整合包导出改真流式

- **位置**：`main.py:751-880`
- **现状**：`BytesIO` 装整个 zip，且逐个 `f.read()` 全量读入 → 3GB 合辑峰值 6GB。
- **方案**：写到 `SpooledTemporaryFile`（超阈值自动落盘），用 `zf.write(path, arcname)`
  让 zipfile 自己分块读；响应头带 `X-Export-Missing`。
- **验收**：导出 2GB 目录常驻内存增量 < 100MB。

### T20 `App.tsx` 永久 rAF 空转

- **位置**：`App.tsx:82-102`（`useSmoothBytes`）
- **现状**：`animate()` 无条件续帧，数字不变也在 60fps 空转，贯穿整个应用生命周期。
- **方案**：差值 < 0.5 时不再续帧，下次目标变化时重新启动。
- **验收**：静止时 `rAF` 计数不再增长。

### T21 工坊更新可取消

- **位置**：`workshop_updates.py:600-605`（硬编码 `cancel=None`）、`main.py:1545-1559`
- **现状**：2GB 更新点下去只能等，没有停止入口。
- **方案**：`start_apply(cancel=event)`；新增 `POST /api/workshop-updates/apply/cancel`；
  更新条上出现「取消」。
- **验收**：更新中途取消，`applying` 状态在 2 秒内变 false。

### 遗留：3 项断言是旧脚本与当前实现不一致，不是本次引入

`scripts/verify_tags_and_conflicts.py` 的 3 项失败已用 `git stash` 对比确认在
改动前就存在：

1. `B 只带 1 个音效文件也算「音效」` —— `tagger.py:343` 现在的规则是
   `f['sound'] >= 3`（注释写明是为了防止"武器包自带 7~11 个音效被误判成音效包"），
   单个音效文件不再满足。断言写于规则收紧之前。
2. `A 与 D 共享 models/ 文件 → 互相算冲突` / `D 侧也标了 A` —— 断言用
   `'D.vpk' in mods['A.vpk'].conflicts` 比较字符串与 `PairConflict` 对象，
   恒为 False。

这三条属于测试自身的陈旧断言，需要产品侧先确认「1 个音效文件该不该算音效」
再决定改测试还是改规则，本次不动。

### 实施中额外修掉的

- `_write_addonlist` 失败时清理 `addonlist.tmp`（原先是留给游戏目录一个垃圾文件）。
- `main.py` 控制台编码判断里的 `GB18032` 笔误（应为 `GB18030`，这段兜底从未生效）。
- `_detect_conflicts` 不再无条件把 `unreadable` 清成 False —— 否则坏包每轮冲突
  重算后都看起来"一切正常"。
- `WorkshopPage` 头像改用 `getApiBase()`（打包版 `file://` 下必然 404）。
