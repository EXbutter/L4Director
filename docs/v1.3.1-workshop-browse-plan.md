# v1.3.1 创意工坊浏览器 · 计划

> 定位：把现在那个「内嵌 steamcommunity 网页」的工坊页，换成**自己画的 Mod 浏览器**：
> 搜索、筛选、排序、看详情、一键下载，全程不离开软件。
> 核心诉求来自用户原话：「至少带筛选」—— 所以筛选是 P0 的第一优先级，其余围绕它服务。

调研基线：`1.3.0`（工作区当前状态）。所有结论都在本机实测过，数据见「数据源调研」。

---

## 一、目标与非目标

### 要做

1. 浏览：工坊列表以卡片网格呈现，带封面、标题、大小、更新日期、订阅数。
2. 筛选：关键词、分类标签（多选）、角色/怪物标签、排序、时间范围、只看未下载。
3. 详情：大图、描述、标签、作者、大小、更新时间，可一键加入下载队列。
4. 状态：已下载的条目标「已在本地」，不重复下载。
5. 离线可解释：拿不到列表时说清原因（需要能访问 `steamcommunity.com`），给出重试与替代路径。

### 明确不做

- **不做 Steam 账号订阅**。订阅要走登录态接口，需要用户密码/token，风险和收益都不对。
  本功能只负责「把 VPK 拿到本地 addons/workshop」，等价于「下载」而非「订阅」。
- **不做评论、评分、收藏**（读取可以，写入不行）。
- 不做 webview 兜底 —— 原页面整块替换掉。

`frontend/src/renderer/components/WorkshopPage.tsx`（204 行）现在是一个**网页浏览器**：

## 三、数据源调研（本机实测，2026-11-14）

结论先放：**没有免 key 的官方搜索接口，列表只能从网页拿；字段全部从免 key 的详情接口补。**

### 3.1 先解释一个矛盾：为什么「检查更新」免 key，「搜索」就要 key

这两件事走的是 Steam 的**两套接口**，鉴权政策本来就不同：

| | 检查更新（已在用） | 搜索/筛选（本方案要的） |
|---|---|---|
| 接口 | `ISteamRemoteStorage/GetPublishedFileDetails` | `IPublishedFileService/QueryFiles` |
| 输入 | **明确的 ID 列表**（`publishedfileids[0..N]`） | 查询条件（tag、排序、时间、关键词） |
| 无 key 实测 | `200`，返 3 条完整字段 | `403 Forbidden — Please verify your key=` |
| HTTP 方法 | 只收 **POST**（GET → 405） | 只收 **GET**（POST → 405） |
| 能做什么 | 已知 ID → 查详情 | **枚举/检索整个工坊** |

按 ID 查详情不构成「检索能力」——不给 ID 什么也拿不到，没法拿来爬库，所以
`ISteamRemoteStorage` 这一整套老接口一直是公开的；而 `QueryFiles` 能翻页枚举全站、
按任意条件筛，Steam 把它归进需要 key 的服务接口（可配额、可追责、可封）。

补充两个实测细节：

- `IPublishedFileService` 下**所有**方法都要 key，不只是 QueryFiles：
  `GetDetails` / `GetUserFiles` / `GetUserFileCount` 无 key 一律 `401 Unauthorized`。
- 试过浏览页的 `format=rss` / `format=json` / `xml=1` 三种变体，**全部返回同一份 HTML**
  （566 KB，60 次 id），没有隐藏的 JSON 出口。

→ 结论：**没有免 key 的搜索路径**。也正因为如此，方案里「HTML 只当搜索引擎、
字段全部回源到免 key 的 `GetPublishedFileDetails`」这个分工是成立的——唯一需要
免 key 想象力的是「哪 30 个 ID」，其余数据都有正式接口兜底。

### 3.2 官方搜索接口 `IPublishedFileService/QueryFiles`

| 尝试 | 结果 |
|---|---|
| POST `api.steampowered.com` | `405 Method Not Allowed`（提示必须用 GET） |
| GET `api.steampowered.com` 无 key | `403 Forbidden — Please verify your key=` |
| GET `api.steamchina.com` 无 key | 同上（403，说明路由存在，只是要 key） |
| GET 带一个 32 位假 key | 同样 403 —— 只校验 key 有效性，没有「游客配额」 |

→ 官方搜索**必须自带 API Key**（免费申请，需 Steam 账号）。可作为 P2 增强，不能作为唯一路径。

### 3.3 网页列表 `steamcommunity.com/workshop/browse/`

实测可达（走 Steam++ 反代 1.7~2.3s；直接走 hosts 也行），HTTP 200，中文界面，558 KB。
页面是新版 React SSR，**没有 `data-publishedfileid` 属性**，但每条目稳定出现一段：

```html
<div class="UNowfeldbNg- Panel">
  <div class="_7-YnTYBrWGM- ... aspectratio_square">
    <a href="https://steamcommunity.com/sharedfiles/filedetails/?id=3838067801" class="...">
      <img src="https://images.steamusercontent.com/ugc/..." alt="Roaming Tank" loading="lazy">
```

**每个条目在 HTML 里出现两次**（封面链接一次、标题链接一次），所以「数出 60 个 id」不能当 60 条。
只认「链接内直接跟 `<img>`」的那一次，恰好一条一个：

```python
CARD_RE = re.compile(
    r'filedetails/\?id=(\d+)"[^>]*>\s*<img[^>]*?src="([^"]+)"[^>]*?alt="([^"]*)"')
```

实测该正则在一页里稳定命中 **30 条**，`alt` 就是标题（含 `\n`、`&amp;` 需清洗）。

### 3.4 URL 参数实测（这决定了筛选能不能做）

| 参数 | 效果 | 证据 |
|---|---|---|
| `p=N` | 生效 | p1 与 p2 的 30 个 id 完全不重合 |
| `browsesort=trend / mostrecent / toprated / mostsubscribed` | 生效 | 三种排序首条各不相同；`mostsubscribed` 与 `trend` 结果一致 |
| `searchtext=<词>` | 生效，中文也行 | `音效` / `gun` 均返回不同结果 |
| `requiredtags[]=Sounds` | **生效，但值必须是工坊内部名** | `Sound`（单数）→ **0 条**；`Sounds` → 30 条 |
| `requiredtags[]=` 多个 | 生效，默认 AND | `Weapons`+`Campaigns` 返回混合结果池 |
| `match_all_tags=1` | 有效，强制交集 | 两组同时带上时与不带结果一致（Steam 默认已按交集） |
| `excludedtags[]=Sounds` | 生效 | `Weapons` 排除 `Sounds` 后与 Sounds 结果交集 = 0 |
| `days=7 / 30` | 生效 | 与默认结果重合仅 9/30 |
| `numperpage=100` | **无效**，恒定 30 条/页 | 长度无变化 |
| `ajax=1` | **无效**，仍返回整页 HTML | 同上 |

**关键坑：`Sound` 与 `Sounds` 一字之差，前者返回空列表，且页面显示「没有项目」，不会报错。**
筛选器里的 tag 值必须用这张表（页面 `role="button"` 里抓到的真实名字）：

```
分类：Campaigns  Weapons  Items  Sounds  Scripts  UI
幸存者：Survivors  Bill  Francis  Louis  Zoey  Coach  Ellis  Nick  Rochelle
特殊感染者：Special Infected  Boomer  Charger  Hunter  Jockey  Smoker  Spitter  Tank  Witch
普通感染者：Common Infected
```

> `Special Infected` 带空格，需 URL 编码；其余可直接拼。

### 3.5 详情字段（免 key，已在线验证）

`GetPublishedFileDetails` 实测返回 **24 个字段**，做卡片和详情抽屉都够：

```
title  description  filename  file_size  file_url  publishedfileid
time_created  time_updated  preview_url  hcontent_preview  hcontent_file
tags[]  subscriptions  lifetime_subscriptions  favorited  lifetime_favorited
views  creator  creator_app_id  consumer_app_id  visibility  banned  ban_reason  result
```

两个要点：

- **`tags[]` 直接带回来**（`[{'tag': 'Tank'}, {'tag': 'Scripts'}]`），不用为「显示标签」再抓一次网页。
- **没有评分（vote_data）**，那是 QueryFiles 才有的字段。卡片上用「订阅数」代替热度。

### 3.6 由此得到的架构

```
前端筛选条件 ──► 后端 /api/workshop/browse
                     │
                     ├─(1) 拼 URL ──► steamcommunity/workshop/browse  ──► 30 个 id + 封面 + 标题
                     │                    （约 1.7~2.3s，HTML 解析）
                     │
                     └─(2) 批量补字段 ──► fetch_details(ids)  ──► 大小/时间/订阅/标签
                                          （约 0.3~0.4s，蒸汽平台端点）
                     └─(3) 合并、按 HTML 顺序重排、标已下载、过滤 banned
```

**HTML 只当搜索引擎用，数据一律以官方详情接口为准。** 这样即使 Steam 改版把卡片改得面目全非，
只要「a > img」这个基本结构还在，解析器就能活；而字段永远是对的。

### 3.7 API Key：申请门槛、法律边界与性能（官方原文 + 本机实测）

#### 申请要求（4 条，第 2 条最容易卡住）

| # | 要求 | 说明 |
|---|---|---|
| 1 | Steam 账号 | 登录 `steamcommunity.com/dev/apikey` 即注册，秒发 |
| 2 | **账号消费 ≥ $5（非受限账号）** | 受限账号的禁用清单里明确含「访问 Steam Web API」。零售 key 激活、免费游戏、市场余额都不算，必须是商店消费/钱包充值 |
| 3 | 填一个域名 | 只是记录用途的标签，不校验归属，`localhost` 也行 |
| 4 | 同意 API 使用条款 | 勾选即可 |

另外：**一个账号只有一个 key**，重新注册会让旧的立即失效；吊销也在这个页面。

#### 法律边界（这条决定了「不能内置 key」）

Steam Web API 使用条款原文（第 2 条）：

> "You agree to keep your Steam Web API key confidential, and not to share it with any third party.
> This license is personal to you and specific to your Application.
> You agree that you will be personally responsible for the use of your Steam Web API key."

以及第 13 条：`You may not transfer, assign, or delegate ... your Steam Web API key to any third party.`

→ **把 key 打包进安装包 = 分发给第三方**，直接违反条款，且 key 泄漏后绑的是开发者账号。
所以 key 只能「用户自己在设置页填」，绝不能内置、不能写进仓库、不能上传到任何云端。

#### 配额

| 项 | 值 | 出处 |
|---|---|---|
| 每日调用上限 | **100,000 次 / 密钥 / 天** | API 使用条款第 2 条原文 |
| 每秒上限 | 未公开 | 文档只提到按 IP 的突发限制 |
| 超限表现 | `429`；持续滥用 → `403` | 社区一致观测 |

对本项目完全够用：单用户浏览一天最多几十次请求，配额是「五个数量级」的富余。
真正的约束是法律边界，不是配额。

#### 性能（本机实测，36 个真实工坊 ID）

| 路线 | 请求数（拿 100 个 Mod） | 单次耗时 | 单次体积 |
|---|---|---|---|
| `QueryFiles`（带 key） | **1 次** | 约 2.5~3.5s（**估算**，见下） | 约 200 KB |
| 网页列表 × 4 页 + 详情 × 1 | 5 次 | 约 **11s** | 约 2.2 MB |

实测基准（三次取样中位数）：

```
GetPublishedFileDetails 36 条   蒸汽平台 1.04s / 72.5 KB     国际站 1.79s
浏览页 30 条（trend）           0.92~3.06s / 555.9 KB
QueryFiles 无 key 的 403 往返   蒸汽平台 0.26s / 国际站 0.41s
```

`QueryFiles` 那行是**估算**：没有 key 拿不到真实成功耗时，只能按「一次请求返回 100 条完整
字段（含 tags/previews/vote_data），payload 与上面 36 条详情同级」来推。给出这个数字的
依据是同一台机器上 36 条详情 1.04s、且体积线性可推。

结论：**带 key 大约快 3~4 倍、请求数少 5 倍、流量省 10 倍**，但这不是必须的——
不开 key 也能用，只是首屏多等 2 秒、翻页慢一点。

#### QueryFiles 比网页多出来的四个能力（值得为它做 T17）

文档里这几个参数是网页拿不到的：

- `totalonly=true` → **精确结果总数**（网页只能靠翻页试）
- `ids_only=true` → 极轻量翻页（只回 ID，字段再批量补）
- `cursor` → 深翻页（`page` 上限 1000 页，cursor 无此限制）
- `query_type=21`（`RankedByLastUpdatedDate`）→ 按**最近更新**排序，网页的 4 种排序里没有
- `return_vote_data=true` → **评分**（这是网页/详情接口都拿不到的唯一字段）

## 四、后端设计

新增文件 `backend/services/workshop_browse.py`（约 350 行），路由挂在 `backend/main.py`。

### 4.1 接口

```
GET  /api/workshop/browse
     q=关键词  tags=分类tag逗号分隔  roles=角色tag逗号分隔
     sort=trend|mostrecent|toprated|mostsubscribed
     days=0|7|30|90   page=1
     hide_owned=0|1   （1 = 只看未下载）
  →  { items:[...], page, has_more, source:"html"|"api",
       took_ms, cached, warning:"" }

GET  /api/workshop/item/{wid}
  →  { id, title, desc_text, desc_html, images:[...], size, updated, created,
       subs, favs, views, tags:[], creator, local:bool, banned:bool }

POST /api/workshop/browse/queue   { ids:["123","456"] }
  →  复用 DownloadManager.add_targets("123 456")，返回 added/ignored
```

`items[]` 字段与前端卡片一一对应：
`id / title / img / size / updated / subs / tags / local / banned`

### 4.2 列表实现要点

1. **URL 构造**（`build_browse_url`）：
   - 固定 `appid=550&section=readytouseitems`
   - `tags` 走 `requiredtags[]`，`roles` 同样（角色也是 tag）
   - 多个 tag 一律追加 `match_all_tags=1`
   - `days>0` 时带 `days=`
2. **HTML 抓取**（`_fetch_browse_html`）：
   - 先走系统路径（吃加速器 hosts / 系统代理），失败再按 v1.3.0 的「禁代理 + 公共 DNS 直连」重试一次
   - `Accept-Encoding: gzip` + 手动解压（与现有下载器一致）
   - 总超时 12s，失败抛 `BrowseError` 带可执行提示
3. **解析**（`parse_cards`）：上面的 `CARD_RE`，去重保序，**上限 30 条**（超出说明混入了推荐位，截断保稳）
4. **补字段**：`fetch_details(ids)`，按 id 建 map 后**按 HTML 顺序重排**（API 不保证顺序）
5. **过滤**：`result != 1`（已删除/私密）与 `banned == 1` 直接丢弃；`hide_owned` 时剔除本地已有的
6. **缓存**：进程内 LRU（`(query_key) → (ts, payload)`），TTL 8 分钟、上限 60 条。
   翻回上一页、改一个筛选又改回来，都不再打网络。
7. **限速**：全局 `_last_html_at`，两次 HTML 请求间隔 ≥ 1.2s（低于这个值 Steam 会开始给 429 空页）
8. **错误分型**，前端按类型给不同文案：
   - `community_unreachable`：DNS 不通 / 连接被拒 / 超时 → 「列表要从 steamcommunity.com 取，当前连不上。开加速器或检查 hosts」
   - `parse_failed`：200 但解析出 0 条 → 「Steam 页面结构变了」，附重试按钮（不要假装「没有结果」）
   - `steam_api_failed`：详情接口失败 → 复用 v1.3.0 的多端点提示

### 4.3 详情实现要点

- `fetch_details([wid])` 单条查（有缓存）
- `description` 是 BBCode（`[b]`、`[url=]`、`[img]`、`[list]`），需要 `bbcode_to_text()`
  与 `bbcode_to_html()` 两级清洗；`[img]` 抽出来放到 `images[]`，正文里不留 `<script>` 类内容
- 图片：`preview_url` 是带参数的 CDN 地址，去掉 `?` 之后的部分也能用；统一走
  `/api/download/thumbnail?wid=&url=` 复用缓存
- `local`：检查 `addons/workshop/<wid>.vpk` 或 `addons/workshop/<wid>/` 存在

### 4.4 与现有代码的接缝

- `workshop_downloader.py` 只加一个公开函数 `fetch_details` 的复用，不改变其行为
- 已下载判断不新建索引，复用 `mod_scanner` 现有的 `workshop_id` 扫描结果（接口层已经算好）
- 不改动 1.3.0 的下载队列语义：浏览页的「下载」只是往队列里塞 ID，进度仍在下载页看

## 五、前端设计

### 5.1 页面结构（替换 `WorkshopPage.tsx`）

```
┌──────────────────────────────────────────────────────────────┐
│ 搜索框（中文/英文）       排序▾   时间▾   已选条件 chips  ✕清除 │
├──────────────┬───────────────────────────────────────────────┤
│ 分类         │  卡片网格（3~4 列，随宽度）                     │
│  ☑ 战役      │  ┌────┐ ┌────┐ ┌────┐                         │
│  ☑ 武器      │  │封面│ │封面│ │封面│                         │
│  ☐ 物品      │  │标题│ │标题│ │标题│                         │
│  ☐ 音效      │  │2.1M│ │已下载│ │8.7M│                        │
│  ☐ 脚本      │  └────┘ └────┘ └────┘                         │
│  ☐ 界面      │                                               │
│              │  ‹ 上一页   第 2 / N 页   下一页 ›             │
│ 角色（折叠） │                                               │
└──────────────┴───────────────────────────────────────────────┘
```

- 左侧筛选栏可折叠（窄窗口 < 1100px 自动收成顶部抽屉）
- 卡片：封面 1:1、标题两行截断、底部一行「大小 · 更新时间」；右上角「已下载」角标
- 卡片点击 → 右侧详情抽屉（不是整页跳转），抽屉内「加入下载队列 / 在工坊打开」

### 5.2 筛选器（P0 的核心，逐项落地）

| 控件 | 行为 | 后端参数 |
|---|---|---|
| 搜索框 | 输入 400ms 防抖后查询；回车立即查 | `q` |
| 分类多选（6 项） | 复选，勾选即查；全不选 = 不限 | `tags` |
| 角色/怪物（折叠，17 项） | 同上 | `roles` |
| 排序 4 项 | 趋势（默认）/ 最新 / 最高评分 / 最多订阅 | `sort` |
| 时间范围 | 不限 / 近 7 天 / 近 30 天 / 近 90 天 | `days` |
| 只看未下载 | 开关 | `hide_owned` |
| 已选条件 | 顶部 chips 展示，单个可删，整组可清空 | —— |

**任何筛选变化一律回到第 1 页**（否则会出现「第 5 页 + 新条件 = 空页」的经典 bug）。

### 5.3 状态与反馈

### 补充：上线后的一次性能事故（2026-11-15）

第一版卡片直接 `<img src={后端封面地址}>`，实测整页 **16 FPS**。定位过程与结论：

| 猜测 | 验证 | 结论 |
|---|---|---|
| 卡片 DOM 太多（100 张） | 100 张卡片、ThumbImage 之后仍 200 FPS | 不是 DOM |
| 毛玻璃 / 背景模糊 | 该页只有 `main` 一层 backdrop-filter，切页后帧率不变 | 不是滤镜 |
| **封面素材** | 缓存目录 507 MB / 245 个文件，其中 **66 个 GIF 共 405 MB，最大 28 MB** | **真凶** |

L4D2 工坊封面里大量 GIF 动图，Chromium 的 `<img>` 会把**全部帧**解码常驻；
一屏十几张就够把主线程压满。「我的模组」早就为同一类素材写了 `ThumbImage`
（首帧静态化 + 按需逐帧解码 + 并发闸门），工坊页绕过了它。

修复四步（前两步各踩了一个坑）：

1. 卡片改用 `ThumbImage`（`animation="hover"`，一次只播一张）。
2. **惰性触发**：一开始只换组件，100 张同时转码，整页反而掉到 **2 FPS** ——
   `canvas.toBlob` 在主线程，几百次编码叠起来更糟。于是加 `lazy`（进视口附近才抓）
   + 全局转码并发上限 4。
3. **封面宽度显式 100%**：卡片是 flex 列，缩略图异步到位前封面是空元素，
   交叉轴把宽度收成 0 —— 图解码成功却完全不可见（排查两轮才定位）。
4. 后端配合：按文件头判 MIME、`fetch_bytes` 保留查询串、缓存 256 MB 上限、
   单张 > 4 MB 不落盘。

关于「让图床先缩放」：接口支持 `?imw=&imh=`，实测能省 90% 流量，但**图床是服务端实时
计算，单张 3~12 秒**（原图走边缘缓存只要 0.2 秒），所以默认不用，只保留能力
（`thumbnailUrl(..., w, h)` 显式传才会带）。尺寸问题交给前端本地降采样解决。

结果：100 张卡片、滚动渐进出图（24 → 48 → 72 → 88），稳定 **195~200 FPS**；
封面缓存 507 MB → 234 MB。白盒断言见 `scripts/verify_workshop_thumb_perf.py`（23 项）。

- 入场：左侧 16px 滑入、0.3s `--ease-soft`、步进 18ms（比卡片 24ms 密，一屏行更多），
  第 25 行起 `animation: none`（同卡片的上限）。

**筛选展开：从「条件渲染」改成「高度插值」**

原实现是 `{isOpen && <div className="wk-group__tags">}` + `animation: wk-group-in`。
问题是 DOM **一挂载就占满高度**，动画只作用在内部元素的透明度/位移上，观感是
「啪」一下弹开；收起时组件直接卸载，没有任何过渡。

改成常驻 DOM：

```scss
.wk-group__body { display: grid; grid-template-rows: 0fr; transition: grid-template-rows .26s var(--ease-soft); }
.wk-group.is-open .wk-group__body { grid-template-rows: 1fr; }
.wk-group__inner { overflow: hidden; min-height: 0; visibility: hidden; transition: visibility 0s linear .26s; }
```

三个必须同时成立的点，少一个就失效（都写成了断言）：

1. **`min-height: 0`** —— grid 子项默认 `min-height: auto`，会被内容撑住，`0fr` 压不下去。
2. **`overflow: hidden`** —— 高度压到 0 后内容还得被裁掉，否则 chip 会画到组外面。
3. **`visibility` 延迟到过渡结束** —— 收起后 chips 不能 Tab 聚焦（`visibility: hidden`
   才不参与焦点顺序），但立刻隐藏会让过渡最后一帧闪空白。

为什么不用 `max-height`：标签组高度从 1 行（类型 4 个）到 4 行（武器 20+）不等，
写死一个够大的 `max-height` 会让缓动失真 —— 前 20% 就走完实际 116px，后 80% 在等空白。

实测（rAF 采样 `getBoundingClientRect().height`）：

| 展开 | 2ms | 20ms | 40ms | 60ms | 86ms | 121ms | 167ms | 250ms |
|---|---|---|---|---|---|---|---|---|
| 高度 | 0 | 7.0 | 30.2 | 56.5 | 82.0 | 102.4 | 112.7 | 116（终值） |

收起同参数反向：116 → 66 → 35 → 17 → 8 → 0，结束时 `visibility` 才转 hidden。
chevron 旋转也调到 0.26s 同缓动，箭头转到位时标签组刚好展开完。

**工具链上踩的三个坑**（`.tmp_preview` 下的脚本，未入库）

- **PrintWindow 会返回过期帧**：窗口不在前台/被遮挡时，`PrintWindow(hwnd, …)` 抓到的是
  上一帧的离屏表面 —— 连拍 6 帧 md5 完全相同，一度误判「点击没生效」。改用
  `Page.captureScreenshot`。
- **CDP 截图 `fromSurface: true` 会卡死**：它要等一次新的 GPU 合成帧，窗口不在前台时
  合成器不产帧，90 秒也不返回。改成 `fromSurface: false`（从窗口表面抓）+ 先激活窗口。
- **WebSocket 分片**：截图返回的 base64 有几 MB，对端会拆成「首帧 + N 个 continuation」。
  `scripts/cdp.py` 原来只认 opcode 0x1/0x2，遇到 0x0 直接跳过继续等下一帧 → 永远超时。
  已修（累积分片直到 FIN）。

**1. key 明文躺在 config.json 里。** 上一版只做到「不进仓库 + 接口回指纹」，但文件本身
是明文的。任何读文件的程序、开了云同步的备份目录、排障时贴出去的 config.json
都能拿到 —— Steam Web API Key 是账号级凭证，可被刷配额、可被判滥用。

改成 DPAPI（`CryptProtectData` + 程序专用熵）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 打开 config.json | `"steam_api_key": "60BA…"` | `"steam_api_key_enc": "dpapi:v1:AQAAAN…"` |
| 别人拿到该文件 | 直接可用 | 解不开（绑定 Windows 账户） |
| 换 Windows 账户 | 照常可用 | 界面提示「解不开，请重填」，不静默当未配置 |
| 想完全不落盘 | 无 | `L4DIRECTOR_STEAM_KEY` 环境变量 |

实现要点：

- `_seal()` / `_unseal()` 用 ctypes 直调 crypt32（不引入 pywin32，打包体积不变）。
  `CRYPTPROTECT_UI_FORBIDDEN` 必加 —— 后端是子进程，弹凭据框会卡死整条链路。
- `_write_config()` 增加 `drop=` 参数：迁移时要把明文字段**删掉**，置空不算清理。
- `_unseal()` 解不开一律返回空串、不抛异常；`key_status()` 用 `readable` 字段区分
  「没配」和「配了但解不开」，前端据此给不同提示。
- 新增 `redact()`：32 位十六进制统统一打成 `****`，4 个接口错误出口全部过一遍。
  `_query_files` 的重试错误只拼 `host：异常类型名`，不带完整 URL（URL query 里有 key）。

**2. 测试脚本里写着真 key 的全文。** `verify_workshop_browse.py` 的掩码断言、
格式校验、存取测试共 6 处直接用了用户那把 key —— 测试数据没有理由用真凭证，
一旦推上去就等于公开。全部换成假串 `0123…CDEF`，CHANGELOG 里的指纹示例也改成
泛指的 `A1B2…9F0E`。

新增 `scripts/verify_secret_hygiene.py`（42 项）覆盖：密文落盘、旧明文迁移、
清除后字段不残留、解不开时 `readable=False`、掩码只露首 4 末 4、`redact` 生效、
接口不回传原文、前端不落 localStorage、`.gitignore` 三条规则、仓库里不存在
`steam_api_key = <32 位>` 形态的赋值（只匹配 key 形态，避免把 md5/CRC 校验值误报）。

**顺带清理**：`.tmp_preview/`（82 个调试帧与探针脚本，163MB）、`frontend/release/`
（v1.0.0 全套产物）、`frontend/out` 里 1.1.0 的安装包、`scripts/_verify_*.txt`、
`__pycache__`。项目体积 2474MB → 2105MB。v1.2.0 的安装包与 blockmap 保留，
发 1.3.1 时还要用它做差分。
